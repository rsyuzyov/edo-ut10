# Профиль базы — шаблон

Логика КОНКРЕТНОЙ базы для расширения «ЦентрУправленияЭДО»: то, чего в типовой УТ 10.3 нет вовсе.
Это отдельное расширение с одним общим модулем `ПЭДО_ПрофильБазы`. Ядро находит его по имени —
в какой бы конфигурации или расширении он ни лежал — и зовёт в четырёх точках.

## Зачем отдельным расширением, а не правкой ядра

Профиль переживает обновление ядра. Обновили `ЦентрУправленияЭДО` — ваш профиль на месте, сливать
ничего не нужно. Ровно это и было мотивом
[issue #2](https://github.com/rsyuzyov/platformaedo-ut103/issues/2): у одной установки поверх
ядра лежало 272 строки своей логики, и обновление 1.0.0.x → 1.1.2.2 дало 8 конфликтных блоков
в 5 файлах.

## 🔑 Что сюда писать, а что нет

**Писать:** свои табличные части (коды маркировки), нетиповые реквизиты отбора, свои узлы XML,
условия готовности, которых нет в типовой.

**Не писать:** вариации самой типовой конфигурации. Ядро определяет их само — отсутствующий
реквизит подставляет, фактические имена видов контактной информации находит запросом,
отсутствующий тип в измерении регистра глушит. Продублируете здесь — будете сопровождать
вручную то, что и так работает.

Чем меньше профиль, тем дешевле обновление ядра. Проверяйте себя вопросом: «это есть в типовой
УТ 10.3 хоть в каком-то виде?» Есть — не сюда.

## Как собрать

Нужна только платформа 8.3.20 или новее, конфигуратор и рабочая база не нужны:

```powershell
build\build.ps1 -Bin "C:\Program Files\1cv8\8.3.27.1964\bin\ibcmd.exe" `
                -Src profile-template\src `
                -Out PlatformaEDO-Profile.cfe `
                -Name ПлатформаЭДОПрофиль -Prefix ПЭДО_ -MinSizeKb 1
```

Ставится как обычное расширение — рядом с `ЦентрУправленияЭДО`, порядок применения не важен.
⚠️ Идентификаторы объектов профиля (`uuid` в `src`) обязаны отличаться от ядра. При совпадении,
например у языка, платформа молча применяет только одно из двух расширений, и ядро профиль
не находит. Копируя шаблон для второго профиля, выдайте ему новые `uuid`.
⚠️ Безопасный режим у профиля снимайте так же, как у ядра, если в профиле есть обращения
к криптографии или внешним ресурсам.

## Контракт версии 1

| метод | поля `Параметры` | когда зовётся |
|---|---|---|
| `ВерсияКонтракта()` | — | один раз на прогон, сверяется с ядром |
| `ПриПроверкеГотовности` | `Ссылка`, `Готов`, `Причина`, `ОтправкаНеТребуется` | перед отправкой документа |
| `ПриФормированииНастройкиКонфигурации` | `Текст` | при сборке запроса списка документов |
| `ПриФормированииНастройкиРеализации` | `Текст` | при сборке маппинга реализации |
| `ПриФормированииXML` | `Ссылка`, `Текст` | после сборки XML, до подписи |
| `ПриОпределенииУчетнойЗаписи` (необязательная) | `УчетнаяЗапись`: `Организация`, `Отпечаток`, `ИдентификаторУчастника`, `ТипПодписанта` (ЮЛ/ИП/ФЛ), `НомерМЧД`, `ДатаМЧД`, `ДолжностьПодписанта` | при каждом чтении учетных записей организаций |

Методы меняют поля структуры на месте; возвращаемое значение не используется.

Необязательную точку можно не объявлять: профиль без нее работает как раньше. Внутри
`ПриОпределенииУчетнойЗаписи` не вызывайте `ЭДО_Сервер.УчетнаяЗаписьЭДО` и функции, которые ее читают
(подпись, токен, `ГидОрганизации`), - это бесконечная рекурсия.

⚠️🔴 **Ошибка внутри профиля останавливает отправку** и приходит наружу текстом
«Профиль базы, метод X: …». Так сделано намеренно: молча отправленный не тот XML уже не
отозвать. Профиля нет вовсе — ядро работает как раньше, это штатный режим.

⚠️ Тексты настроек приходят ПОСЛЕ автоподстановок ядра — вы правите готовый текст,
а не собираете его с нуля.

## Носитель расписания: если в базе нет типового задания ядра

Регламенты ядра (отправка очереди, сверки, сторожа, автоприёмка) запускаются экземплярами
типового задания `ЗаданиеОбменЭлектроннымиДокументами`: ядро перехватывает его метод в
`МодульРегламентныхЗаданий` и по параметру задания (ключу) выбирает регламент. В конфигурациях,
где этого задания нет (например, КА 1.1), носитель делает профиль:

1. уберите `МодульРегламентныхЗаданий` из состава ядра при сборке (см. INSTALL);
2. в профиле заимствуйте любое **непредопределённое** задание своей конфигурации **без
   экземпляра в базе** (значит, платформа его не запускает и типовая логика им не пользуется)
   с методом на **один параметр** — и общий модуль этого метода;
3. в перехвате метода зовите разводку ядра:

```bsl
&Вместо("ВыполнитьОбменДаннымиДляНастройкиОбмена")   // метод выбранного задания
Процедура ЭДО_ВыполнитьОбменДаннымиДляНастройкиОбмена(КодНастройки)
	// Ядро - другое расширение: прямое обращение к его модулю компилятор профиля не
	// разрешает, поэтому через Выполнить. Наш ключ - регламент выполнен, чужой -
	// типовое поведение нетронуто.
	Выполнено = Ложь;
	Выполнить("Выполнено = ЭДО_Регламенты.ВыполнитьРегламентПоКлючу(КодНастройки)");
	Если НЕ Выполнено Тогда
		ПродолжитьВызов(КодНастройки);
	КонецЕсли;
КонецПроцедуры
```

4. экземпляры заданий заводите на **этом** задании, с тем же параметром-ключом, что и у ядра:
   список ключей — `ЭДО_Регламенты.КлючиРегламентов()`.

Разводка «ключ → регламент» одна и живёт в ядре (`ЭДО_Регламенты.ВыполнитьРегламентПоКлючу`):
новый регламент ядра профиль подхватывает без правки, достаточно завести экземпляр задания.

## Совместимость

`ВерсияКонтракта()` должна совпадать с `ПЭДО_Сервер.ВерсияКонтрактаПрофиля()` ядра.
Не совпала — ядро откажется вызывать профиль и скажет об этом, вместо того чтобы работать
наполовину.

Контракт считается нестабильным, пока живых профилей меньше трёх: если вам не хватает точки
или состава параметров — заводите issue, менять сейчас дёшево.
