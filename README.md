# Расширение 1С:Управление торговлей 10.3 для ЭДО через «Платформа ЭДО»

Отправка исходящих УПД (СЧФДОП) формата **5.03** из УТ 10.3 оператору ЭДО
[«Платформа ЭДО»](https://edo.platformaofd.ru): сборка титула продавца, ФЛК оператора,
**подпись КЭП на стороне сервера 1С**, отправка и запись результата обратно в базу.

🔑 **Ключевое отличие от коробочного сценария — подпись выполняется на сервере.** Контейнер КЭП
лежит в реестре под учёткой службы кластера, сертификат — в её личном
хранилище.

## Требования

- **1С:Предприятие 8.3.18+** для работы (режим совместимости расширения — `Version8_3_18`)
- **1С:Предприятие 8.3.20+** для сборки — исходники выгружены в формате **2.17**
- **УТ 10.3** (обкатано на 10.3.88.3);

⚠️ Версию формата XML-выгрузки выбрать нельзя: её штампует та платформа, которая выгружает,
и режим совместимости на это не влияет. Старшая платформа читает более ранние форматы, младшая
новые — нет. Поэтому дерево держим в 2.17 (8.3.20–8.3.24): так исходники открываются и на 8.3.2x,
и на 8.5. ⟹ **выгружать `src` обратно только платформой 8.3.20–8.3.24**, иначе формат уедет вверх
и соразработчики на 8.3.x потеряют доступ к исходникам.

## Установка

Пошаговый путь для чистой типовой УТ 10.3 — **[INSTALL.md](INSTALL.md)**: поднять режим
совместимости (без этого расширения в базе не работают вовсе), установить `.cfe`, завести
свойства объектов и задать обязательные настройки. Там же — вариант установки без
конфигуратора, через `ibcmd`.

## Логика своей базы — отдельным расширением

Если в вашей базе есть то, чего в типовой УТ 10.3 нет вовсе (свои табличные части с кодами
маркировки, нетиповой реквизит отбора, свои узлы XML), это пишется не правкой ядра, а
**профилем базы** — отдельным расширением с общим модулем `ПЭДО_ПрофильБазы`. Ядро зовёт его
в четырёх точках, а обновление ядра профиль переживает без слияний.

Шаблон и описание контракта — [profile-template/](profile-template/README.md).

Необязательная точка `ПриИзмененииСостоянияДокумента` сообщает профилю, что документ ушёл оператору,
сменил статус при сверке или аннулирован: профиль может отразить это в своих регистрах. Зовётся
только при реальной смене, сбой профиля пишется в журнал (`ЭДО.ПрофильСостояния`) и не ломает отправку.

## Готовая сборка

Собранный `.cfe` каждой версии — на вкладке
[Releases](https://github.com/rsyuzyov/platformaedo-ut103/releases), рядом лежит файл с SHA-256.
Номер релиза совпадает с `<Version>` расширения: `v1.0.3.3` = `1.0.3.3` в свойствах расширения
в базе, так что установленную сборку всегда видно.

⚠️ SHA-256 годится для проверки скачанного файла, но не для сверки со своей пересборкой:
`.cfe` из одних и тех же исходников каждый раз выходит другим (замер — три сборки подряд:
869 312, 868 602 и 869 316 байт). Контейнер 1С хранит служебные метки, и совпадения байт в байт
от него ждать нельзя.

## Сборка `.cfe` из исходников

```powershell
powershell -ExecutionPolicy Bypass -File build\build.ps1 `
    -Bin  'C:\Program Files\1cv8\8.3.24.1439\bin\ibcmd.exe' `
    -Src  '.\src' `
    -Out  '.\PlatformaEDO.cfe'
```

## Выпуск релиза

Собрать `.cfe` в облачном раннере нельзя — нужна платформа 1С, поэтому релиз выпускается
с машины, где она установлена:

```powershell
powershell -ExecutionPolicy Bypass -File build\release.ps1 -DryRun   # прогон без публикации
powershell -ExecutionPolicy Bypass -File build\release.ps1           # тег + релиз на GitHub
```

Скрипт берёт номер из `src/Configuration.xml`, находит `ibcmd` сам (предпочитая 8.3.20–8.3.24),
собирает `.cfe`, считает SHA-256, ставит тег `v<версия>` и публикует релиз через
[`gh`](https://cli.github.com/) с заметками из истории коммитов. До сборки он отказывается
работать, если рабочая копия не чиста, ветка не `main`, локальная `main` разошлась с `origin`
или тег такой версии уже есть — во всех этих случаях выпущенный файл не соответствовал бы тегу.

Ключи: `-Bin` (путь к `ibcmd.exe`), `-Out` (каталог артефактов, по умолчанию `dist\`),
`-NotesFile` (свои заметки вместо сгенерированных), `-Draft`, `-SkipChecks`.

## Проверки исходников

`build/checks.py` проверяет то, что читается без платформы: версия расширения, версия формата
выгрузки, разбор XML, отсутствие в публичном дереве следов конкретной базы и — главное — что
версия поднята, если `src` менялся после последнего релиза. Тот же скрипт гоняется в GitHub
Actions на каждый push и pull request.

```powershell
python build\checks.py
```

## Ветка `vendor`: сверка с обработкой вендора

Ветка `vendor` — чистые выгрузки обработки «Платформа ЭДО» в том виде, в каком её отдаёт вендор
(`platformaofd.ru/pdf/edo-files/ofd-edo.rar`): по коммиту на версию, теги `vendor/1.0.5.3.4.1`,
`vendor/1.0.5.3.8`. При импорте пути маппнуты под наше дерево (`ОФД_ЭДО` → `ЭДО_ПлатформаЭДО`),
поэтому сверка — обычный `git diff`:

- что изменил вендор между своими версиями: `git diff vendor/1.0.5.3.4.1..vendor/1.0.5.3.8`;
- наши правки относительно вендора: `git diff vendor/1.0.5.3.8..main -- src/DataProcessors/ЭДО_ПлатформаЭДО/`.

⚠️ Сверять в первую очередь по модулям `.bsl`: XML-метаданные дают шум формата выгрузки
(выгрузка вендора сделана платформой 8.5.1, наш `src` держит формат 2.17).
⚠️ Содержимое ветки `vendor` не правится: новая версия вендора — новый коммит с тегом.

## Настройка

Порядок первой установки целиком — в [INSTALL.md](INSTALL.md); ниже — что именно настраивается.

Всё настраивается из одного места — формы **«Настройки ЭДО»** обработки `ПЭДО_Помощник`.
До первой отправки достаточно открыть её и выполнить два действия: **«Завести свойства
объектов»** и заполнить отпечаток сертификата подписанта.

Форма показывает состояние готовности: пока обязательное не задано, она перечисляет, чего
не хватает, а отправка отказывается работать с той же причиной вместо ошибки платформы.

### Что настраивается

| параметр | смысл | по умолчанию |
|---|---|---|
| `ОтпечатокПодписанта` | отпечаток сертификата КЭП (Base64) — **обязателен**, в коде его нет | — |
| `ДатаНачалаОтправки` | дата запуска ЭДО в бой; раньше неё документы не берутся никогда — **обязательна** | — |
| `ГлубинаДнейОтправки` | второе ограничение окна отбора | 30 |
| `ЛимитДокументовЗаПрогон` | сколько документов уходит за один прогон | 100 |
| `ГотовыеСтатусыЗаказа` | статусы заказа покупателя, при которых документ готов к отправке | `Отгружена,ПереданаНаОтгрузку` |
| `Хост` | адрес API оператора | `edo.platformaofd.ru` |
| `ГлубинаДнейСинхронизацииСтатусов` | окно опроса статусов у оператора | 14 |
| `ТаймаутHTTPСек` | таймаут обращений к оператору | 30 |
| `ПрочиеНашиАдресаЭДО` | наши ящики у других операторов, через запятую | — |
| `АвтоматическоеПринятиеУПД` | 1 — принимать входящие УПД от контрагентов с флагом без участия человека | 0 |
| `ДопускСуммыУПД` | режим по сверке: допустимая разница суммы с НДС и суммы НДС между базой и УПД, руб. | 0.01 |
| `ПоискПоступленияМесяцевНазад` | режим по сверке: окно поиска поступления относительно даты УПД, назад | 4 |
| `ПоискПоступленияМесяцевВперёд` | режим по сверке: окно поиска поступления относительно даты УПД, вперёд | 1 |

🔑 **Нижняя граница отбора = что ПОЗЖЕ: `ДатаНачалаОтправки` или «сегодня минус
`ГлубинаДнейОтправки`».** Каждое ограничение закрывает свой отказ: без даты начала документ,
ставший годным позже (статус связи чинится задним числом), выпадает из скользящего окна
навсегда; без глубины выборка растёт вечно. Действующее окно показано на форме и печатается
в лог отправки.

⚠️ `ГотовыеСтатусыЗаказа`: состав перечисления `СтатусыЗаявок` в базах различается —
несуществующие имена молча игнорируются, поэтому список можно держать общим.

### Свойства объектов

Расширение хранит состояние в типовом механизме свойств (ПВХ `СвойстваОбъектов` + регистр
`ЗначенияСвойствОбъектов`) — своих регистров не заводит, поэтому установка не требует
реструктуризации базы и монопольного режима.

Кнопка «Завести свойства объектов» создаёт недостающие (идемпотентно):
`ОФД_ЭДО_СтатусДокумента`, `ОФД_ЭДО_ИдентификаторДокумента`,
`ОФД_ЭДО_ИдентификаторУчастникаЭДО`, `ОФД_ЭДО_СтатусСвязи`, `ПЭДО_Статус`.

Отдельно, под маппинг реквизитов подписантов, могут понадобиться:
`ОФД_ЭДО_Фамилия/Имя/Отчество` (продавец), `ОФД_ОРГ_Фамилия/Имя/Отчество` и
`ОФД_ОРГ_Должность` (узел `Подписант`), `ОФД_КА_Фамилия/Имя/Отчество` (контрагент).

⚠️ Ресурс `Значение` регистра — **Строка(50)**: списки и длинные значения туда не влезают,
поэтому кэши и настройки расширение держит в `ХранилищеОбщихНастроек`.

### Автоматическое принятие входящих УПД

Регламент подписывает титул покупателя на входящие УПД от доверенных продавцов. Документ в базе
не создается: принятие у оператора, а поступление заводится как обычно.

1. Кнопкой «Завести свойства объектов» создать свойство `ЭДО_АвтоматическоеПринятиеУПД` (Булево,
   вкладка «Свойства» карточки контрагента) и отметить им доверенных продавцов. Флаг действует
   на ИНН: достаточно отметить одну карточку, если у продавца их несколько.
2. Сухой прогон — `ЭДО_Сервер.ВыполнитьАвтоматическоеПринятиеУПД(Истина)`: пишет в журнал
   регистрации (`ЭДО.Регламент.АвтоматическоеПринятиеУПД`), что было бы принято. Работает и при
   выключенной настройке.
3. Включить настройку `АвтоматическоеПринятиеУПД` = 1.
4. Завести экземпляр регламентного задания `ЗаданиеОбменЭлектроннымиДокументами` с параметром
   `ЭДО_АвтоматическоеПринятиеУПД`, наименование «ЭДО: автоматическое принятие УПД», например
   каждые 15 минут.

Берутся УПД за 14 дней в статусе `SENT` или `DELIVERED`, кроме счетов-фактур без функции ДОП,
не больше 50 за прогон. Титул подписывается КЭП сервера — тем же сертификатом, что и отправка.
Если титул создан, а подпись не прошла, следующий прогон подписывает его же, второй не создается.

#### Режим по сверке

Для части продавцов «слепое» принятие рискованно: хочется убедиться, что в базе есть
подходящее поступление и суммы совпадают, а не просто довериться флагу контрагента.

1. У контрагента, у которого уже стоит `ЭДО_АвтоматическоеПринятиеУПД`, дополнительно
   поставить флаг `ЭДО_СверкаПередПринятиемУПД` (Булево, тоже на вкладке «Свойства»). Один
   флаг без другого ничего не меняет — сверка работает только у уже доверенных продавцов.
2. Перед подписью регламент скачивает содержимое УПД у оператора, берёт из XML сумму с НДС
   и сумму НДС, ищет в базе `Документ.ПоступлениеТоваровУслуг` этого продавца с тем же
   номером (сравнение без учёта регистра, пробелов, дефисов и ведущих нулей) в окне вокруг
   даты УПД и сравнивает суммы с допуском.
3. Сошлось — титул подписывается как обычно, в свод прогона попадает пометка «по сверке
   с <поступление>». Не сошлось (поступление не найдено, найдено несколько, не проведено
   или суммы расходятся больше допуска) — титул НЕ подписывается, документ остаётся ждать
   человека, причина уходит в свод прогона строкой «НЕ СОШЛОСЬ» и в журнал сверки.
4. Три настройки сверки — `ДопускСуммыУПД`, `ПоискПоступленияМесяцевНазад`,
   `ПоискПоступленияМесяцевВперёд` (см. таблицу настроек выше).

Причины смотреть двумя способами: в журнале регистрации (`ЭДО.Регламент.АвтоматическоеПринятиеУПД`,
строки «НЕ СОШЛОСЬ») и вызовом `ЭДО_Сервер.ЗагрузитьЖурналСверкиВходящих()` — он отдаёт
Соответствие по Ид входящего документа за последние 90 дней (Когда, Номер, Дата, ИННПродавца,
Продавец, Организация, Поступление, Сошлось, ОтклонениеСуммы, Причина).

На самом найденном поступлении (когда кандидат ровно один) регламент пишет три свойства:
`ЭДО_ВходящийИдентификатор` (Ид документа у оператора), `ЭДО_ОтклонениеСуммы` (разница сумм
с НДС), `ЭДО_ПричинаНепринятия` (короткая причина, пусто — если сошлось). Свойства не
обязательны для формы — это диагностика, читать её проще через журнал сверки.

### Хранение настроек

Объект `ОФД_ЭДО_НастройкиОбработки`, **имя пользователя пустое** — настройки общие для всех.

⚠️🔴 Записывать настройки только через форму или `ПЭДО_Сервер.УстановитьНастройкуЭДО()`.
`ХранилищеОбщихНастроек.Сохранить(...)` без пятого параметра кладёт значение **в настройки
текущего пользователя**: расширение прочитает его только из-под того, кто настраивал.
Для баз, настроенных так раньше, на форме есть кнопка «Перенести настройки в общие».

Служебные ключи там же и настройками не являются: `РеестрАдресов`, `ФактическиеМаршруты`
(кэш маршрутов), `ЗамокОтправки` (защита от параллельных прогонов), `КлиентскиеНастройки`
(XML движка вендора).

Журнал сверки входящих УПД (режим по сверке) лежит в **своём** объекте хранилища —
`ЭДО_ЖурналСверкиВходящих`, ключ `Записи`, тоже с пустым именем пользователя. Отдельный
объект, а не ключ в `ОФД_ЭДО_НастройкиОбработки`: это журнал, а не настройка, и его читают
через `ЗагрузитьЖурналСверкиВходящих()`, а не через форму настроек.



## Приглашения контрагентов

Обработка **«Центр управления ЭДО»** (`ЭДО_ЦентрУправления`), закладка **«Приглашения»** —
кому уже звали, кто принял, у кого связь уже есть, кому ещё не звали и приглашение прямо
с этой страницы.

Список строится по контрагентам с отгрузками за выбранный период (тот же отбор, что и на
закладке «Контрагенты»). Адрес берётся собственный (`ЭДО_АдресКонтрагента`), а если его нет —
первый пригодный кандидат из кэша реестра адресов ФНС, тот же источник, что использует
`ПригласитьНовыхКонтрагентов`. Оператор определяется по префиксу адреса штатным способом
(`ЭДО_Сервер.ИмяОператораЭДО`, справочник операторов — из макета вендорской обработки).

Состояние читается ТОЛЬКО из кэша (`ЭДО_Сервер.КэшСостоянийПриглашений`, хранилище общих
настроек, объект `ЭДО_СостоянияПриглашений`) — страница открывается без единого сетевого
запроса. Актуальность кэша поддерживает кнопка **«Обновить состояние»**
(`ЭДО_Сервер.ОбновитьСостоянияПриглашений`): она опрашивает связи и статусы приглашений по
адресам из текущего списка, не больше 300 за один вызов (остаток — в свод прогона). Приглашения
шлются кнопками **«Пригласить выделенных»** и **«Пригласить всех, кому не звали»**
(`ЭДО_Сервер.ПригласитьПоСписку`) — обе спрашивают подтверждение с числом адресов: рассылка
уходит наружу, к оператору, и повторное приглашение по живой связи её рвёт (см. ниже).

⚠️🔴 **`FAILED` с текстом «уже настроен активный маршрут» — это НЕ отказ.** Оператор Платформы
отвечает так на приглашение к абоненту, с которым роуминг уже настроен: связь есть и документы
пойдут. Правило живёт отдельной функцией `ЭДО_Сервер.СостояниеПриглашенияПоОтвету` с
комментарием — проверено на бою 25.09.2026: у 452 из 1774 контрагентов такой ответ, и прямой
опрос связей (`contacts`) по ним даёт `ESTABLISHED`. Без этой проверки такие контрагенты
показывались бы отказавшимися, хотя обмен с ними уже идёт.

## Проверка кодов маркировки

Обработка **«Центр управления ЭДО»**, закладка **«Разбор»**, кнопка **«Проверить коды в
Честном знаке»** над списком документов — необязательная ручная проверка, ничего не
блокирует и не меняет в документах (включая выгрузку в УПД). Берёт выделенные строки, а
если ничего не выделено — текущую; не больше 50 документов за раз. Сверяет коды маркировки
ТЧ `КИЗ` с Честным знаком: владелец кода должен совпадать с организацией документа, а
статус — быть `INTRODUCED`: те же условия, по которым подключаемый модуль Контур.Диадок
исключает коды из выгрузки.
Результат — окно с разбивкой по документу: сколько кодов в порядке, сколько чужие (с кем
перепутан владелец), сколько не в обороте, сколько вовсе не нашлось в Честном знаке.

Точка целиком в профиле базы (`ПриПроверкеКодовМаркировки` в `ЭДО_ПрофильБазы`) и
необязательна: у ядра своего способа обращения в Честный знак нет, он есть только там,
куда поставлен свой общий модуль интеграции (`лионИнтеграцияЧестныйЗнак`). На базе без
него или без профиля кнопка честно скажет, что проверка не поддержана.

## Честный знак: фиксация пива

Для товарной группы «Пиво» Честный знак требует до передачи УПД покупателю зафиксировать
документ в ГИС МТ («разрешение на отгрузку», документ FIX, п. 99 ПП РФ № 2173). Фиксацию делает
сам оператор Платформа: документ проходит статус `AWAIT_FIXATION`, затем уходит покупателю либо
получает `FIXATION_FAILED`. Отдельного метода «создать фиксацию» в API нет — оператор подаёт FIX,
только если сама УПД собрана так:

- **флаги имени файла** — `ИдФайл` 5.03 кончается `_N2_N3_N4_N5_N6_N7`; для пива нужно
  `_0_1_1_0_0_00`: N3 = 1 (маркировка) и N4 = 1. Без N4 Платформа FIX не подаёт (ответ поддержки:
  «имя документа не содержит флага товарной группы Пиво»), ЧЗ отвечает ошибкой 71. Движок вендора
  N4 не ставит вовсе, N3 — только по реквизиту `СодержитМаркируемыйТовар`;
- **реквизиты перевозки** в `ИнфПолФХЖ1` (`ТекстИнф`): `НомерПеревозДок`, `ДатаПеревозДок`
  (dd.MM.yyyy), `РегНомер` (госномер ТС), у покупателя-ИП ещё `Покупатель_ФиасИД`;
- **КПП мест деятельности** — ЧЗ ищет место по ИНН + КПП из УПД. С головным КПП юрлица попадает
  в офис, который в ЕГАИС как место торговли заблокирован: ошибка 189 `ModIsBlockedInEgais`.
  Продавцу и грузоотправителю нужен КПП склада, покупателю и грузополучателю — КПП точки.

Это делает ядро (`ЭДО_Сервер.ДополнитьXMLДляФиксации`, после точки `ПриФормированииXML`).
Пиво и безалкогольное пиво определяются по типовому `Номенклатура.ВидПродукцииИС` (`Пиво`,
`ПивоВПотребительскихУпаковках`, `БезалкогольноеПиво` — какие есть в перечислении). Флаг N3
ставится любому документу с `НомСредИдентТов`. Откуда взять перевозку и КПП мест, знает только
база — необязательная точка профиля:

`ПриПолученииСведенийОПеревозке(Параметры)` — `Ссылка`, `НомерДокумента`, `ДатаДокумента`,
`ГосНомер`, `ФиасИДПокупателя`, `КППОтгрузки`, `КППРазгрузки`, `Ошибка`. Зовётся только для
реализаций с пивом. Без неё (или без номера, даты, госномера, ФИАС у ИП) пивной документ не готов
к отправке — причина видна в «Центре управления». Кириллицу в коде ФИАС ядро заменяет латиницей.

Экземпляр в `FIXATION_FAILED` покупателю не передан и дублем не считается: исправленный документ
отправляется заново. Аннулировать такой экземпляр Платформа не даёт (409).

Итог фиксации расширение читает: `ЭДО_Сервер.СостояниеФиксацииГИСМТ(Ссылка)` спрашивает раздел API
«ЭДО — ГИС МТ» (`GET /edm-crpt/public/api/v3/partner/documents/{id}?subscriber_gid=...`) по
идентификатору документа у оператора и возвращает структуру с итоговой строкой.

Итог хранится в необязательном свойстве документа `ЭДО_СтатусГИСМТ` (заводится кнопкой
«Завести свойства объектов»). Его обновляет регламент «Сверка статусов»
(`ЭДО_Сервер.ОбновитьСтатусыФиксацииГИСМТ`, не больше 200 документов за прогон, в окне полной
сверки; прогон, упёршийся в лимит, запоминает позицию (дата и ссылка документа) — настройка `ГИСМТ_ОбходДо[_ИНН]` — и следующий
продолжает с более старых документов); сбой этой части не ломает основную сверку и пишется в журнал (`ЭДО.ГИСМТ`,
`ЭДО.Регламент.ФиксацияГИСМТ`). В карточке документа значение показано строкой «Честный знак».

| Итог | Что значит | Опрашивается снова |
|---|---|---|
| Зафиксирован в ЧЗ | state = SUCCESS, документ зафиксирован | нет |
| Фиксация не требуется | оператор ответил 404 или пусто, и в документе нет пива | нет |
| Фиксация у оператора не найдена | 404 или пусто, но в документе пиво: FIX ещё не подан | да |
| Обрабатывается в ЧЗ | фиксация идёт (IN_PROGRESS, NEW и т. п.) | да |
| Ошибка ЧЗ: ... | state или status = FAILED, дальше текст lastError | да |
| Фиксация отменена в ЧЗ | операция FIXATION_CANCEL завершена | да |
| Нет данных: ... | запрос не удался (HTTP-код или сеть), прежнее значение не затирается | да |

## Ограничения и известные грабли

- маппинг в макете `НастройкаРеализация` **привязан к конкретной конфигурации базы**: он
  обращается к реквизитам документа реализации, именам видов контактной информации и составу
  перечисления статусов заказа. На другой базе эти места придётся сверить — они снабжены
  комментариями прямо в макете;
- маппинг лежит **в макете расширения**, а не в настройке базы ⟹ любая его правка требует
  пересборки `.cfe`;
- ⚠️ макет — это XML, а BSL лежит внутри его узлов. Сырые `<` и `>` в комментариях BSL ломают
  разбор макета, и сборка документов падает уже в бою. Экранировать (`&gt;`) или не писать;
